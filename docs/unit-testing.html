Unit testing · NestJS + Vitest

Arrange, Act, Assert

A working reference, built from the webhook signature guard in pr-reviewer. The vocabulary and the judgment calls carry to any codebase; the examples happen to be yours.

Every test has the same three beats

A unit test puts one piece of code in a known situation, runs one thing, and checks one claim about what came back. That shape has a name, and naming it is most of the battle when you're staring at an empty .spec.ts.

1 — ARRANGE

Build the world

Construct the thing under test and everything it needs. Nothing is asserted yet.

2 — ACT

Call it once

A single call. If you need two, you probably want two tests.

3 — ASSERT

Make one claim

State what should be true. One reason to fail, so red tells you something.

it('allows a request whose signature matches the body', () => {
  // Arrange
  const body = '{"action":"opened"}';
  const context = contextFor({ body, signature: sign(body) });

  // Act + Assert
  expect(guard.canActivate(context)).toBe(true);
});
In your reposrc/guards/signature.guard.spec.ts — the first worked example. The remaining cases are it.todo stubs waiting for you.

The name in it(...) is the sentence that prints when it fails at 2am. Write it as behaviour — rejects a body that was tampered with after signing — not as mechanics like test canActivate 3.

Deciding what "the unit" is

The unit is the class or function you're making claims about. Everything else it touches is scenery, and scenery should be cheap. In Nest there are two ways to stand a unit up, and picking wrong is the most common reason a test suite turns slow and brittle.

SituationUseWhy
A plain class with constructor dependencies — guards, services, pipes new Guard(stub) No DI container, no resolution errors, milliseconds to run.
You need Nest to interpret decorators — controller routing, guards attached to routes, interceptors Test.createTestingModule Only Nest can wire what the decorators declare.
You're checking real HTTP status codes end to end *.e2e-spec.ts A different job with a different config — not a unit test.

GithubSignatureGuard takes one constructor argument, so it needs no container at all:

const config = { getOrThrow: () => WEBHOOK_SECRET } as unknown as ConfigService;
const guard = new GithubSignatureGuard(config);

When you do need the container, keep it minimal and say out loud what isn't under test. Your controller spec pulls in the guard through a decorator, so it swaps in one that always allows:

Test.createTestingModule({
  controllers: [AppController],
  providers: [AppService],
})
  .overrideGuard(GithubSignatureGuard)
  .useValue({ canActivate: () => true })
  .compile();
Why it mattersWithout that override the suite failed with Nest can't resolve dependencies of the GithubSignatureGuard — a test about a greeting string, broken by HMAC verification it never calls.

The pull toward adding the real ConfigService to providers is strong and worth resisting. Satisfy an unrelated dependency with the real thing once, and the test now needs a .env; do it a few more times and it needs a database and a network, and your fast feedback loop is gone.

The four words people use interchangeably

"Mock" gets used for all of these, which is why the topic feels muddier than it is. The distinctions are small but they change what you assert.

Stub
Returns a canned value. Knows nothing, records nothing. Your fake ConfigService. Reach for this by default.
Spy
Wraps a real function so you can see whether it was called, while it still works. vi.spyOn(Logger.prototype, 'warn') — used in your spec to keep expected warnings out of the output.
Mock
A stub you also assert against — "this was called once, with these arguments." Use sparingly. Asserting on calls couples the test to how the code works, not what it does.
Fake
A real but simplified implementation — an in-memory store standing in for a database. Worth building when many tests need the same substitute.

Vitest gives you vi.fn(), vi.spyOn() and vi.mock() for these. Whichever you use, undo it afterwards — a spy left installed leaks into the next test and produces failures that move around when you reorder files:

afterEach(() => {
  vi.restoreAllMocks();
});

An assertion that's too loose is worse than none

This is the sharpest lesson your guard has to teach, and it's a real bug that was in the code.

crypto.timingSafeEqual throws when the two buffers differ in length. So a malformed signature didn't return 401 — it threw a RangeError, which Nest turns into 500 Internal Server Error. Any client could force a 500 with a one-character header.

Now look at the two ways to write that test:

// Passes whether the guard returns 401 or crashes with a 500.
// It would have gone green on the broken code.
expect(() => guard.canActivate(context)).toThrow();

// Passes only on the error type Nest maps to 401.
// This is the test that catches it.
expect(() => guard.canActivate(context)).toThrow(UnauthorizedException);

Both are green on correct code. Only the second is red on the bug. When you assert that something fails, assert how — the specific error, the specific status, the specific message. "It threw" is almost never the claim you actually mean.

What earns a test

Worth writing
  • Branches you own. Every if that can reject, every early return.
  • Boundaries. Empty, missing, zero, wrong length, wrong type.
  • Anything security-shaped. A signature check should be the best-tested code you have.
  • Every bug you fix. Write the failing test first, then fix it. It never comes back.
Skip it
  • The framework. Nest maps UnauthorizedException to 401. That's their test.
  • Getters with no logic. Nothing can break.
  • Private internals. Test through the public method, or the first refactor breaks everything.
  • Coverage for its own sake. 100% with loose assertions catches less than 60% with sharp ones.

A useful check before writing one: what change to the source would make this go red? If nothing plausible would, the test is decoration.

Reading the runner

npm test runs every **/*.spec.ts once. Your suite as it stands:

✓ src/app.controller.spec.ts (1 test)
✓ src/guards/signature.guard.spec.ts (2 tests | 5 todo)

 Test Files  4 passed (4)
     Tests  9 passed | 5 todo (14)

Three glyphs to know: ✓ passed, × failed, □ skipped or todo. An it.todo is a named test with no body — a to-do list the runner keeps honest, visible on every run instead of buried in a comment.

CommandWhen
npm testOnce, before committing.
npm run test:watchLeave running while you work — reruns only what changed.
npm run test:covFind untested branches. A map, not a score.
npm run test:e2eThe separate *.e2e-spec.ts suite with its own config.
Config notevitest.config.ts sets globals: true, which is why describe, it, expect and vi work without imports.

Finishing the guard suite

Five it.todo stubs are waiting, each with a hint in the comment above it. Run npm run test:watch and take them one at a time.

  1. Wrong secret — sign the right body with 'not-the-secret'.
  2. Tampered body — sign one payload, send a different one.
  3. Malformed header — a valid digest with sha256= stripped off.
  4. Wrong-length signature — 'sha256=abc'. Assert UnauthorizedException, not bare toThrow().
  5. Missing or empty raw body — no body, and separately an empty string.

To prove a test is real, break the source on purpose: delete the length check in the guard and watch cases 3 and 4 go red. A test you've never seen fail is a test you haven't finished writing.
