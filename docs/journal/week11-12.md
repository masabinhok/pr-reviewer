# Week 11–12 Build Guide: What gets posted

## Context

Weeks 9–10 built an evaluation and pointed it at the reviewer. The answer was uncomfortable and
useful: on the held-out fixtures the local model **finds 81% of the known bugs** — and **posts
none of them**. Two things stand between finding and posting:

- **Severity says nothing.** The model rates real bugs low or medium and noise high, so the posting
  bar (high) is a filter on a number that carries no signal. Lowering the bar to medium was
  measured, and it posted more noise for a recall gain inside the spread.
- **The second look throws away two real bugs in three.** With it off, held-out recall goes from
  29% to 81%, with false positives inside the baseline's range. But it is the only thing standing
  between the model's confident nonsense and the pull request, so turning it off is not the answer
  either.

Weeks 11–12 fix the decision itself: **the checker that already reads every finding should say how
sure it is, and that — not the model's own severity — should decide what a person sees.** Then two
things that make the App usable by someone else: `/review` to ask for a review, and a per-repo
config file.

Everything still runs for free, on the local model, on this machine.

---

## Definition of done

Weeks 11–12 are complete when all of these are true:

1. **Ten new held-out fixtures**, built the same way as the others, each key checked by hand. The
   nine that decided weeks 9–10 are retired into the tuning set — they have been read finding by
   finding and can no longer decide anything.
2. The agent's second look answers with **how sure it is**, not just yes or no; the API stores it
   and the dashboard shows it.
3. **Whether a finding is posted is decided by that judgement**, in one function the publisher and
   the evaluation both call — never two copies of the rule.
4. The evaluation decides whether that change is kept: on the new held-out set, over three runs,
   **posted recall beats the baseline by more than the spread without more false comments per clean
   pull request**. Kept or reverted, the numbers are written down.
5. **`/review` in a pull request comment** runs a fresh review, and only for someone allowed to ask.
6. **`.prreviewer.yml`** in the reviewed repository can ignore paths and set the posting threshold;
   a broken config is reported on the pull request, never silently ignored.
7. `docs/evals/report.md`, the README's headline and `docs/decisions.md` are current, and the
   roadmap's weeks 11–12 are ticked.

### Traps — read before starting

**1. A held-out set is new only once.** The ten new fixtures decide milestone 38. Do not read their
findings while tuning, do not print them, do not "just check" one. Everything else — the tuning
split, the old held-out fixtures now retired into it — is fair game.

**2. Every change to the checker costs an hour of GPU.** The stamp covers the agent's prompts and
settings, so a kept change needs a full run (87 reviews) before CI will pass. Tune on the tuning
split first (`--split tune`, three runs, about 35 minutes), and spend the full run only on a change
worth keeping.

**3. Confidence may be as meaningless as severity.** The model rates its own findings badly; there
is no reason to assume it rates its own *checks* well. Before building a posting rule on the
checker's confidence, measure on the tuning split whether findings it is sure about are right more
often than findings it is unsure about. If they aren't, that is the result — write it down and try
the other lever (asking the checker for a severity, or asking a second checker).

**4. `/review` is a command from a person, and the internet can comment.** Check the comment's
author association (owner, member or collaborator), ignore bots, ignore comments on closed pull
requests and on issues that aren't pull requests. The per-pull-request lock already exists: one
review at a time, so a dozen `/review` comments can't queue a dozen reviews.

**5. A repository's config file is untrusted input.** It comes from the head commit of a pull
request anyone can open. Cap its size, parse it against a schema, ignore unknown keys, never let a
path in it escape the repository, and never let a broken one fail the review silently — say what is
wrong, review with the defaults.

**6. Per-repo config must not quietly change what the evaluation measures.** The fixtures carry
their own request; the config of the repository a fixture came from has nothing to do with it. Keep
config out of the eval's path, or the numbers stop meaning the same thing run to run.

## Milestone 36 — A fresh held-out set

- Ten new bug fixtures from real fixes, at least five from repositories not already used, built with
  `npm run eval:fixture` and keyed by hand. Two or three clean fixtures with them, so the new set
  can answer "does this post noise?" as well as "does this find bugs?".
- The nine spent held-out fixtures become `tune`, with a note in each saying when and why. The split
  is a property of the fixture, so this is a one-line change per file — and an honest one.
- A full evaluation run at the end: the committed baseline doesn't cover the new fixtures, so the
  gate fails until one does. That run is also the baseline the new held-out numbers are measured
  against.

## Milestone 37 — The checker says how sure it is

- The `verdict` tool gains a judgement of how likely the finding is to be a real defect worth a
  comment — the checker's own rating, not the reviewer's. Reason first, as now.
- It travels the contract: the agent returns it per finding, the API stores it beside the verdict,
  the dashboard shows it, and the evaluation records it.
- **Calibration, measured on the tuning split** (trap 3): of the findings the checker is most sure
  about, what share are right, against the ones it is least sure about? The answer decides whether
  milestone 38 is worth building — and is worth writing down either way.

**Todo**
- [ ] The tool and prompt change, with the agent's tests
- [ ] Contract, storage, dashboard, and the eval's results
- [ ] Calibration on the tuning split, three runs, written down
- [ ] `docs/decisions.md`: what was asked for, and why that shape

**Learn:** whether a small model knows what it knows — and how to measure that.

## Milestone 38 — Posting decided by the judgement

- One function decides whether a finding becomes a comment, from the checker's judgement and verdict
  (with severity at most a tiebreak), called by the publisher and by the evaluation.
- Tuned on the tuning split, then decided on the new held-out set, with the rule for keeping it
  **written and committed before that run**.
- Kept or reverted, `docs/evals/report.md` gets the attempt and its numbers; if the headline moves,
  so does the README.

## Milestone 39 — `/review`

- `issue_comment.created` whose body starts with `/review`, on a pull request, from someone allowed
  to ask (trap 4), queues a review of the pull request's head commit.
- The App has to be subscribed to the event and may need another permission; whatever it needs goes
  in the README's setup section.
- Acknowledge visibly: a 👀 reaction on the comment when the review is queued, and the existing
  Check Run carries the rest. A comment that isn't a command, or isn't from an allowed person, does
  nothing at all — no reply, no reaction.

**Todo**
- [ ] The event handled, and the App subscribed (setup documented)
- [ ] Authorisation, bots and closed pull requests refused
- [ ] One review at a time per pull request
- [ ] e2e: a command queues a review, a stranger's doesn't

**Learn:** commands from the outside world, and who is allowed to spend your GPU.

## Milestone 40 — `.prreviewer.yml`

- Read from the head commit of the pull request under review: paths to ignore, and the posting
  threshold for this repository. Size-capped, schema-parsed, unknown keys ignored (trap 5).
- The filters and the posting rule take it as an argument — no globals, and nothing in the
  evaluation's path (trap 6).
- A broken config is reported in the Check Run summary, naming the key, and the review runs with the

## Verification checklist

When weeks 11–12 are done (ask Claude to "verify week 11-12"):

1. The final run reproduces the README's number within its spread, and CI's gate passes on it.
2. The ten new held-out fixtures each have provenance and a hand-checked key; the retired ones say
   why they were retired; no held-out finding was read before the milestone-38 decision.
3. The posting rule exists once: grep finds no second copy of it in the evaluation or the scripts.
4. `/review` from a collaborator queues a review; from a stranger or a bot, nothing happens.
5. A `.prreviewer.yml` that is huge, malformed, or full of unknown keys doesn't fail a review, and
   its problem is visible on the pull request.
6. Anti-patterns to grep for: the checker's judgement read anywhere but the one posting rule, config
   reaching the evaluation, a decision made on a held-out set that was already read.
