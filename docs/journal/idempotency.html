pr-reviewer · milestone 5

Let the Database Decide

GitHub delivers webhooks at least once, not exactly once. Milestone 5 is one idea — stop asking whether you have seen a delivery before, and let the unique constraint answer — plus the plumbing to make it real in this repo.

Why the same delivery arrives twice

GitHub’s webhook delivery is at-least-once. Three things cause a repeat, and all three send the same X-GitHub-Delivery value with an identical payload:

  • 01Your endpoint takes longer than about ten seconds, GitHub times out and retries — while your first run may still be working.
  • 02Someone clicks Redeliver in the App’s Recent Deliveries page.
  • 03You returned a 5xx, so GitHub retries on its own schedule.

Without a guard, a redelivered pull_request.opened runs your reviewer twice: two Claude API calls billed, two check runs, two identical sets of inline comments on one pull request. That is the failure this milestone exists to prevent.

The obvious fix has a hole in it

The version everyone writes first reads the table, then decides:

// WRONG — two concurrent redeliveries both see "not found"
const seen = await prisma.webhookDelivery.findUnique({ where: { deliveryId } });
if (seen) return;
await prisma.webhookDelivery.create({ data: { deliveryId, event, action } });

This is a time-of-check to time-of-use race. Between the read and the write there is a window where the row does not exist yet, and any second request that looks during that window sees an empty table and draws the wrong conclusion.

The window is small, but it is exactly the window GitHub’s timeout-retry aims at: the retry fires because the first request is slow, which means the first request is still in flight. And once you run more than one instance behind a load balancer, the two requests are not even in the same process — no lock, mutex, or in-memory set in your application code can see both of them.

Only one component sees every writer

Postgres does. Your schema already declares deliveryId as @unique, and that constraint is the lock — it is enforced inside the database, across every connection, every process, and every instance. So stop asking permission and just write. The failure is the answer:

try {
  await this.prisma.webhookDelivery.create({ data: { deliveryId, event, action } });
} catch (e) {
  if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2002') {
    return { ok: true, duplicate: true };   // 200, but skip the handler
  }
  throw e;
}

P2002 is Prisma’s error code for “unique constraint failed.” The instanceof check earns its keep twice: a bare e.code === 'P2002' will not typecheck when e is unknown under strict mode, and narrowing to the known-request type stops you swallowing some unrelated error that happens to carry a code property.

in your repoThe error class comes from the generated client: import { Prisma } from '../generated/prisma/client.js', then Prisma.PrismaClientKnownRequestError.

A duplicate is not an error

The single most important line in that snippet is ok: true. A duplicate must return 2xx.

Return a 500 instead and you have built a machine that generates its own load: GitHub sees the error, retries the delivery, the retry is also a duplicate, which also 500s, which triggers another retry. Worse, sustained 5xx responses are what make GitHub mark the endpoint unhealthy and eventually stop delivering at all.

Reframe it: a duplicate arriving is not a fault to report. It is the redelivery mechanism working exactly as designed, and your correct response is a calm acknowledgement plus a log line saying you dropped it.

Where the write goes in the request

Ordering matters here in a way it rarely does, because two of these steps have a hard constraint on which side of the response they sit.

  1. 01Verify the signature Done in Milestone 4. GithubSignatureGuard rejects anything unsigned or tampered before the handler is reached, so nothing untrusted ever reaches the database.
  2. 02Insert the delivery row A P2002 here means stop: acknowledge and skip the handler. This has to happen before the response, because the row is the idempotency record — acknowledge first and crash before writing it, and the redelivery looks brand new.
  3. 03Return 200 GitHub’s clock is running from the moment it opened the connection. Everything expensive belongs on the far side of this line.
  4. 04Handle the payload Today this is one log line. In weeks 3–4 it becomes a BullMQ enqueue — and because the acknowledgement already happened at step 3, that swap changes nothing above it.
  5. 05Record the outcome Set processedAt and move status off RECEIVED. A handler that threw is recorded as failed with its error, not silently dropped — a row stuck at RECEIVED forever is how you find out something died.
andStep 2 is service work, not controller work. WebhooksService — the empty stub you deleted — is what this milestone was waiting for. The controller keeps reading headers and returning a shape; the service owns the database and the decision to dispatch.

Three gaps in the schema

WebhookDelivery was designed back in Milestone 3 and mostly fits, but the checklist asks for things it cannot store yet.

no error column

The todo says failed handlers are recorded with the error, not silently swallowed. You have status but nowhere to put the message. Review already carries error String? for exactly this reason — the same field belongs here.

status is a String, not an enum

Your own docs/decisions.md argues at length that state fields must be Postgres enums, because a plain String lets "compelted" insert cleanly and then silently fail every query filtering on the exact value. WebhookDelivery.status is the one state field that never got the treatment. Either add a DeliveryStatus enum or write down why this one is different — an inconsistency with a recorded reason is a decision; an unexplained one is a smell.

action is required, but not every event has one

action String, with no ?. Every pull_request payload carries payload.action, so you are fine today — but you record deliveries for unhandled events too, and a push payload has no action field at all. Make it nullable now, or meet it the first time you widen HANDLED_EVENTS.

One thing the schema got right: installationId stays null for now. It is a foreign key to Installation, and no installation rows exist until Milestone 7 — writing an ID that is not there would fail the constraint. Nullable was the correct call.

Two wiring problems, waiting

Both of these bite the moment you inject PrismaService, and neither is about idempotency — they are just next in line.

PrismaModule is never imported

app.module.ts imports ConfigModule, HealthModule and WebhooksModule. There is no PrismaModule anywhere in the tree.

You will get the same Nest can’t resolve dependencies error you have already seen twice — once from the guard needing ConfigService, once after the webhooks refactor.

@Global is imported but not applied

prisma/prisma.module.ts imports Global on line 1, but the class carries only @Module({...}). The decorator was never written.

So even adding the import to AppModule will not expose PrismaService inside WebhooksModule. Decorate the class, or add imports: [PrismaModule] to the webhooks module. Global is conventional for a database client.

Testing a claim about the database

The checklist item is same delivery ID twice → one row, handler invoked once. Everything you have tested so far has been a pure function fed a hand-built fake. This one has a real dependency, and that changes the question.

Unit test, faked Prisma

Stub webhookDelivery.create so the first call resolves and the second rejects with a PrismaClientKnownRequestError carrying code: 'P2002'. Assert your handler spy was called exactly once.

Fast, no database, runs anywhere — but it asserts against your belief about what Postgres does, and you wrote both the belief and the test.

Integration test, real Postgres

It is already in Docker. Call the service twice with the same delivery ID, then count the rows. A beforeEach that truncates the table is enough isolation.

Slower and needs cleanup — but it actually proves the constraint exists and fires, which is the entire claim of the milestone.

Given that this whole design rests on “trust the database,” the integration test is the one that tests the thing you are claiming. Write it deliberately rather than mocking your way around the dependency — learning where the seam belongs is most of the value here.

The polish bar

Milestone 4 ended at a terminal with curl and a hand-computed signature. This one ends in GitHub’s own UI, which is a better test because it is the real client:

  • →Open Recent Deliveries in your App’s settings and hit Redeliver on a delivery you have already processed.
  • →Confirm GitHub shows a 2xx, not a red response.
  • →Confirm select count(*) from "WebhookDelivery" where "deliveryId" = ... returns exactly 1.
  • →Confirm a log line says the duplicate was dropped, tagged with the same delivery ID you have been threading through since Milestone 4.
